Bathroom humidity · status light

Answers one question: did someone shower and leave the window shut? A normal shower and a stuck one look identical at their peak — what separates them is where things settle afterwards. So the light reads the shape of the curve over time, not how high it got.

Everything is measured against the level the room sat at just before the shower, taken fresh from the trace each time. No fixed percentages and no long-run average, so a humid Tel Aviv summer and a dry winter both work with no retuning — and a spell of sensor downtime cannot skew the reference.

The counter-intuitive part. An aired-out bathroom does not promptly return to its previous level: wet towels, walls and floor keep evaporating, so it plateaus a couple of points above and sits there. Flat does not mean stuck. A shut window shows itself by plateauing far above where it started — so the test is the size of what is left, not the mere fact that it stopped falling.

The knobs

ConstantValueWhat it decides
HUM_RISE_DELTA6 pts Size of jump that marks a shower — this is what keeps slow damp out of it.
HUM_RISE_WINDOW_MIN15 min How fast that jump has to happen.
HUM_PRE_WINDOW_MIN30 min How much quiet time before the rise defines the “before” level.
HUM_CLEARED_MARGIN2.5 pts Close enough to “before” to call it recovered. The amber↔green dial.
HUM_GRACE_MIN30 min Grace period before a shower is even considered a problem.
HUM_FALLING_DROP1 pt / 20 min Still coming down this fast counts as clearing, however far it has to go.
HUM_STUCK_EXCESS6 pts Gone flat this far above “before” = trapped steam. The amber↔red dial.
HUM_SMOOTH_MIN5 min Median window for “current”, so one noisy sample cannot flip the light.

Worked example — the shower that broke the first version

04 Sep · window opened, then a shower · reads AMBER
Quiet at 63.7 % all morning → spike to 74.7 % at 09:56 → fast fall to ~67.6 % by 10:14 → flat at 67–68 for the next 35 min.
Now 66.1 %, which is +2.6 pts above the pre-shower level. Flat, yes — but only just above where it started, so: aired out, still drying → amber. Nearly green.
Had the window been shut it would have parked near 72–74, i.e. +9, and gone red.
The bug this exposed. Version one compared against the 24 h 25th-percentile, which the sensor's first hours online had dragged down to 60.4 % — 3 points below the room's real quiet level. It then asked “recovered ≥ 50 % of the peak?”, landing on 0.49–0.60 against a 0.50 threshold, so sensor noise alone flipped the light red and back every minute. Both faults are gone: the reference is now taken from the trace itself, and “current” is a 5-minute median.
Implemented as humidity_status() in server.py — a pure function, so HumidityStatusTest can exercise it against synthetic traces (quiet · recovered · stuck · still-falling · no-spike drift · dry winter room · open-window plateau · window opened before the shower · single noisy sample). Decided server-side because it needs 6 h of history, far more than the board is sent.
Thresholds were derived from the sensor's own data and are provisional — worth revisiting once a few weeks of real showers exist to check them against.
